# Self-review

## Принятые решения

1. **Единая точка приёма серверного состояния.** Все ответы проходят через `applyServerView`: старая ревизия отбрасывается, `deleted` окончателен. Этим одним правилом закрыты `stale_status`, ответ `queued/rev 1` на повторный POST и поздний ответ после удаления.
2. **Логика отделена от платформы.** `StatementImportService` — обычный класс с внедряемыми репозиториями по подходу шаблона, поэтому сбои и перезапуск тестируются по настоящему HTTP против неизменённого mock: перезапуск имитируется новым сервисом на том же хранилище. Цена в том, что `StatementFileRepository` с нативным кодом автотесты не покрывают.
3. **Копия файла живёт ровно до подтверждения job.** Ключ сохраняется до первой отправки, а копия нужна только для повтора с теми же байтами. После перезапуска приложение только читает состояние; повторно отправить файл может лишь пользователь.

## Что упростил ради срока

- Одна активная операция, без очереди импортов.
- При потере временной копии приложение просит выбрать файл заново, а не восстанавливает её.
- Опрос раз в секунду без отдельного backoff при обрыве сети.
- Отчёт хранится локально, чтобы устаревший ответ после перезапуска не оставил экран без данных. Это больше минимума, но запись удаляется вместе с операцией.

## Что сломается первым в production

- **Сервер без `chunked`.** Отправка идёт с диска потоком только благодаря заголовку `Transfer-Encoding: chunked`: без него `react-native-blob-util` на iOS читает файл в память целиком. Mock такой запрос принимает, но часть серверов и хранилищ запрос без заранее известной длины отклонит, и тогда придётся менять способ отправки.
- **Очистка кэша ОС** между потерей ответа и повтором: тогда пользователь выбирает файл заново. Если первая попытка всё же дошла до сервера, а `by-key` не успел её показать, новый выбор создаст новый ключ и второй job.
- **Обновление `react-native-blob-util`.** На Android библиотека сама повторяла POST при обрыве соединения, поэтому файл уходил второй раз без пользователя, а восстановление по ключу не срабатывало. Второго job не было благодаря ключу, но поведение я убрал патчем. При обновлении библиотеки его нужно проверить заново, а автотесты этот нативный код не покрывают. Заметил это только по счётчику `createRequests` на эмуляторе.
- **Как заметить:** сейчас телеметрии нет. Нужны счётчики без данных файла: доля импортов в неопределённом исходе, `failed: localCopyLost`, отношение созданных job к подтверждённым отправкам.

## AI-инструменты

Использовался Claude Code: код, тесты и прогоны на эмуляторах.

Он также участвовал в выборе способа отправки файла. В React Native я больше работал с `multipart/form-data`, чем с прямой отправкой `application/octet-stream`, поэтому варианты разбирал вместе с ним. Он предложил библиотеки и по исходникам `react-native-blob-util` показал, что поток с диска на iOS включается заголовком `Transfer-Encoding: chunked`.

С его помощью сделана и подписка на состояние в `StatementImportService`: `subscribe` и список листенеров, через которые `useSyncExternalStore` обновляет экран. Также с его помощью сделан `StatementFileRepository` для работы с файлами: выбор файла, временная копия, чтение начала файла и отправка с диска.

Сам прошёл матрицу на симуляторе iOS и эмуляторе Android: сверял экран со счётчиками `createRequests` и `newJobs` на экране диагностики и закрывал приложение после `lost_ack`.
